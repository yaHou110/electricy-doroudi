# Data Model

This document describes the actual persistence model as implemented in `prisma/schema.prisma`. It answers: what entities exist, how they relate, what is immutable, what may be deleted, and which constraints the database enforces. Documentation must match implementation; when the schema changes, this document changes in the same commit.

## Entity overview

```text
User (staff account)
  ├── StockMovement   (actor)
  ├── Sale            (seller)
  └── ProductPriceHistory (changedBy)

Product
  ├── Brand?          (each product has at most one)
  ├── Category?       (each product has at most one)
  ├── ProductPriceHistory
  ├── GoodsReceiptLine
  ├── SaleLine
  └── StockMovement

Supplier ──< GoodsReceipt ──< GoodsReceiptLine >── Product
Customer ──< Sale ──< SaleLine >── Product

Warehouse? ──< StockMovement
```

Cardinalities:

* `Product → Brand/Category`: many-to-one, optional (`SetNull` on delete).
* `GoodsReceipt → GoodsReceiptLine`: one-to-many, lines die with the receipt (`Cascade`).
* `Sale → SaleLine`: one-to-many, lines die with the sale (`Cascade`).
* `StockMovement`: references `Product` and `Actor (User)` (required) and `Warehouse` (optional). Movements are never orphaned (`Restrict` on all three).
* `ProductPriceHistory`: required `Product` (`Cascade`) and `changedBy` User (`Restrict`).

## Conventions

| Concern      | Convention |
| ------------ | ---------- |
| Identifiers  | UUID v4 generated by Prisma (`@default(uuid()) @db.Uuid`) for every table. |
| Money        | Exact integers in Rial (`BigInt`): `costPriceRial`, `salePriceRial`, `unitCostRial`, `unitPriceRial`, `totalRial`, `creditLimitRial`, `purchasePriceRial`. No floats. API inputs accept a JSON integer or decimal string and coerce to `BigInt`; API responses serialize `BigInt` as a **decimal string** (`lib/serialize.ts`), so values stay lossless at any magnitude. |
| Time         | `DateTime` columns stored in UTC; `createdAt`/`updatedAt` on every aggregate root. |
| Quantities   | Positive integers; direction comes from the movement `type`, not the sign. |
| Soft delete  | Not used. Deactivation is modeled as a flag (`Product.isActive`); history rows are never rewritten to hide a record. |
| Extensibility| Product technical specs live in `Product.attributes` (JSONB); everything that needs filtering, indexing, or integrity is a real column. |

## Enums

* `UserRole`: `MANAGER`, `WAREHOUSE`, `SALES` — one role per user (RBAC, see `SECURITY.md`).
* `StockMovementType`: `RECEIPT`, `SALE`, `ADJUSTMENT_IN`, `ADJUSTMENT_OUT`, `RETURN_IN`, `RETURN_OUT`. Inbound types (`RECEIPT`, `ADJUSTMENT_IN`, `RETURN_IN`) increase stock; the rest decrease it.
* `SaleStatus`: `COMPLETED`, `VOIDED` — `VOIDED` is reserved for the future void/return workflow; nothing sets it yet.
* `CustomerType`: `RETAILER`, `CONTRACTOR`, `COMPANY`, `OTHER`.

## Immutability and source of truth

* `StockMovement` is the inventory ledger and the single source of truth for stock. Current stock is always derived: `sum(+inbound) − sum(outbound)`. There is no mutable stock counter anywhere in the schema.
* Movements keep a traceable link to their business document via `referenceType` + `referenceId` (e.g. `GOODS_RECEIPT` → receipt id, `SALE` → sale id).
* `ProductPriceHistory` is the price audit trail; current prices on `Product` are the operational read model. Line items on receipts and sales snapshot the price at posting time and never follow the product's current price.
* Immutability is enforced at the application layer (code only ever inserts movements; no route updates or deletes them). There is no database trigger blocking `UPDATE`/`DELETE` on the ledger — this is a deliberate Milestone 1 trade-off, see "Known gaps".

## Deletion rules (what the database enforces)

* `SetNull` — deleting a Brand/Category nulls the product's reference; deleting a Supplier nulls `GoodsReceipt.supplierId`; deleting a Customer nulls `Sale.customerId`. History keeps its meaning.
* `Cascade` — deleting a GoodsReceipt or Sale removes its lines; deleting a Product removes its price history.
* `Restrict` — a Product with movements or transaction lines cannot be deleted; a User with movements or sales cannot be deleted; a Warehouse with movements cannot be deleted. Business history is never orphaned or silently destroyed.

## Unique constraints (business keys)

| Table                | Unique column   | Business meaning |
| -------------------- | --------------- | ---------------- |
| `User`               | `email`         | Login identity. |
| `Warehouse`          | `name`          | One warehouse per name. |
| `Brand` / `Category` | `slug`          | Stable taxonomy identity. |
| `Product`            | `sku`           | Item identity. |
| `GoodsReceipt`       | `receiptNo`     | Idempotency key for receiving retries. |
| `Sale`               | `saleNo`        | Idempotency key for sales retries. |

The receipt/sale numbers are the MVP idempotency keys, with precise semantics defined in `API.md`: a retry with the same number and the same normalized payload (canonical fingerprint from `lib/idempotency.ts`) returns the original result without a second write; the same number with a different payload is a hard `409` conflict — the stored document is never modified.

## Indexes

Secondary indexes exist for the query paths actually used: `Product(name, brandId, categoryId)`, `ProductPriceHistory(productId, changedAt)`, `GoodsReceipt(receivedAt)`, `GoodsReceiptLine(productId)`, `Sale(soldAt)`, `SaleLine(productId)`, `StockMovement(productId, occurredAt)`, `StockMovement(warehouseId)`, `StockMovement(referenceType, referenceId)`, `Customer(name)`.

## Transactional invariants

* Receiving and selling run inside a single `Serializable` Prisma transaction that writes the document, its lines, and all movements atomically — partial failure leaves nothing behind.
* Each stock-changing transaction first takes `SELECT … FOR UPDATE` on every referenced `Product` row (deterministic id order) via `lockProductRows`; the sales transaction then derives current stock from the ledger and rejects (`INSUFFICIENT_STOCK`) if any line would push stock below zero.
* Serialization failures (`P2034`) are retried up to 3 times with exponential backoff (`runSerializableTransaction`); a failed attempt writes nothing, so retries cannot double-apply stock effects. Exhaustion surfaces as HTTP 503.
* Duplicate business numbers (`receiptNo`/`saleNo`) surface as constraint violations and are mapped to the idempotent replay/`409` behavior above.

## Known gaps (honest list)

* `StockMovement.warehouseId` is nullable and current write paths do not set it. The model is warehouse-ready; wiring receipts/sales to the default warehouse is pending. **Stock is therefore system-wide, and no UI or API may present it as warehouse-specific** until write paths populate the column.
* Ledger immutability is by application convention only (no DB trigger/rule).
* `SaleStatus.VOIDED` exists but no void/compensation workflow is implemented; corrections are not yet possible through the API.
* `User` has no activation/lock flag yet; "manage users" is roadmap, not implementation.
